# Identity Provider

Identity provider support lets a server synchronize an external directory into
the local identity cache, provision selected cached identities as managed
Trojan users, and use provider groups in server redirect access policies.

The feature is server-side only. Runtime traffic and service diagnostics read
Live artifacts. Desired inputs remain the operator-owned source of truth.

## Direction of synchronization

Synchronization is pull-based. The xp2p server connects to the configured
directory endpoint and reads users, groups, and memberships. The provider does
not connect back to xp2p and does not push identity changes into xp2p.

The tested SCIM-like provider is Keycloak:

```text
xp2p server -> Keycloak Admin API users
xp2p server -> Keycloak Admin API groups
xp2p server -> Keycloak Admin API group members
```

For Keycloak, `kind = "scim"` means that xp2p reads a SCIM-like directory shape
from the Keycloak Admin API. A normal OIDC ID token or Authorization Code flow
is not a directory API and is not enough for synchronization.

## Core model

An xp2p server can select zero or one identity provider. A provider is
identified by a stable `instance_id` and `kind`.

Supported provider kinds:

- `ldap` for LDAP directories.
- `scim` for Keycloak Admin API and other SCIM-like directory APIs.

The synchronized cache is stored under `.state/identity/state.json` in the
configuration root. It records:

- schema version and selected provider;
- current and pending generations;
- sync status, last success time, and last error;
- external subject IDs and generated managed labels;
- group IDs, display names, and direct memberships;
- `provisioned` and `detached` lifecycle flags.

Managed labels are generated by xp2p and use the reserved `idp-...` namespace.
Manual users cannot create, import, or rename a user into that namespace.

## Provider configuration

Provider configuration lives in `xp2p-server.toml`.

LDAP example:

```toml
[server.identity_provider]
instance_id = "corp-directory"
kind = "ldap"
secret = "reader-password"
group_ids = ["engineering", "admins"]

[server.identity_provider.ldap]
url = "ldap://ldap.example.internal:389"
base_dn = "dc=example,dc=internal"
bind_dn = "cn=xp2p-reader,ou=service,dc=example,dc=internal"
user_filter = "(objectClass=inetOrgPerson)"
group_filter = "(objectClass=posixGroup)"
subject_attribute = "employeeNumber"
membership_attribute = "memberUid"
display_name_attribute = "displayName"
```

Keycloak example:

```toml
[server.identity_provider]
instance_id = "corp-keycloak"
kind = "scim"
secret = "keycloak-service-account-token"
group_ids = ["engineering", "admins"]

[server.identity_provider.scim]
endpoint = "https://keycloak.example.internal/admin/realms/corp"
```

`secret` is the LDAP bind password or Keycloak bearer token unless a
provider-specific token is configured. Configuration export and diagnostic
bundles include this plaintext configuration; normal CLI output, logs, audit
events, and UI responses must not print provider secrets.

## Scope

`group_ids` is the synchronization scope.

An empty scope synchronizes the full directory. A non-empty scope synchronizes
the selected groups, their nested groups, and all reachable members. Group IDs
are stable provider IDs, not display names.

When a successful full snapshot no longer contains a subject, group, or
membership, or the object is no longer reachable from the configured scope,
xp2p removes it from the current cache generation. Failed or partial snapshots
never perform deletion.

Nested groups are resolved transitively. Cycles are rejected as an invalid
provider snapshot.

## Normal operation

Synchronize the identity cache:

```sh
xp2p server identity sync
```

Inspect identity state:

```sh
xp2p server identity status
```

Provision a cached identity as a managed server user:

```sh
xp2p server identity provision idp-example@xp2p.local
```

Use a provider group in a restricted redirect:

```sh
xp2p server redirect add --domain internal.example --access restricted --allow-group engineering
```

## Discovery and provisioning

First discovery allocates a managed label in the identity cache only. It does
not create a Trojan user, credential, reverse portal, connection link, Xray
inbound user, or redirect.

Provisioning is the explicit privileged action that creates local tunnel
resources for one cached identity:

- a managed Trojan user and credential;
- a reverse portal;
- a connection link in the command result;
- `provisioned = true` in the identity cache.

Only the provisioning result reveals the generated credential and link.

The managed label cannot be renamed. Removing the managed user through normal
server user administration removes the local user, credential, portal, and
bound local state, but only clears `provisioned`; it does not remove the cached
identity.

## Authoritative removal

A successful full provider snapshot is authoritative for objects in scope.

If a previously synchronized subject is removed from the provider or leaves the
configured scope, xp2p removes that cached identity from the current generation.
If the subject was provisioned, xp2p may also remove identity-manager-owned
local resources:

- the managed Trojan user and credential;
- the managed reverse portal;
- redirects bound to that managed portal.

Unrelated user-managed files and unrelated manually managed users are not
modified. Unrelated redirects that mention the old label as an explicit ACL
user keep that unknown label.

If the same person later appears again as a new provider subject, xp2p treats
it as a new identity, allocates a new managed label, and requires provisioning
again.

## Provider detach and reattach

Removing or replacing the selected provider is non-destructive. Cached
identities and currently provisioned local resources become detached. Detached
cache entries remain inspectable, but they are not usable for group resolution
or identity-dependent compilation.

Detach the selected provider:

```sh
xp2p server identity detach
```

Reattach or select a provider:

```sh
xp2p server identity select corp-directory --kind ldap
```

If the selected `instance_id` matches the cached generation, the generation is
reattached. Selecting a different provider keeps the old cache detached until a
successful sync creates a compatible generation. A later authoritative
successful snapshot for the matching provider instance is the operation that
may remove managed resources.

## Redirect access policy

Identity provider groups are used only by `server_redirects`. Server forwards
and Xray reverse control routes are system mechanics and are outside this ACL
model.

Redirect access policy fields:

```toml
[[server.server_redirects]]
domain = "crm.office.local"
outbound_tag = "office.rev"
access = "restricted"
users = ["client-k3x7@xp2p.local"]
groups = ["engineering"]
```

Policy rules:

- no users or groups means public access;
- `access = "all"` is public even when selectors are present;
- selectors imply `restricted` when `access` is omitted;
- `access = "restricted"` requires at least one selector;
- explicit user labels are retained even when no local peer exists;
- groups resolve to transitive members, then labels are deduplicated;
- only provisioned identity-managed subjects contribute active local labels;
- if a restricted policy resolves to no active labels, the Xray rule is omitted
  and the effective state is `disabled_by_policy`;
- empty, deleted, or out-of-scope groups are fail-closed and do not make the
  Desired file invalid by themselves.

Provisioning does not grant redirect access by itself. The redirect must still
allow the label explicitly or through a provider group.

## Cache freshness

`server.identity_provider.max_cache_age` controls how long a successful sync can
be used for identity-dependent compilation. The default is `24h`.

When the cache is missing, detached, or stale:

- identity status remains available;
- already running Live configuration is not changed solely because time passed;
- new server candidates that require identity resolution fail;
- xp2p does not silently fall back to public access.

## Full and partial snapshots

Synchronization expects a complete provider snapshot. A successful complete
snapshot can add, update, and delete cached identities and memberships.

Failed or partial snapshots leave the previous current generation unchanged.
This prevents temporary provider errors, timeouts, size limits, pagination
problems, or malformed membership data from deleting local access state.

LDAP membership must resolve from provider membership values to immutable
subject or group IDs. Malformed, ambiguous, or unresolved references make the
snapshot invalid. Keycloak/SCIM-like sync uses stable resource IDs from the
directory API.

## Transactions and recovery

Identity operations are serialized by a server-wide identity operation lock.
The lock covers sync, provisioning, provider changes, and identity-dependent
redirect changes.

Runtime-capable operations follow the same strict apply flow as other server
changes:

1. Build a candidate state in memory.
2. Compile and validate the server candidate.
3. Record a transaction with previous and candidate identity, Desired, and Live
   hashes.
4. Apply supported Xray changes through gRPC when the service is running.
5. Verify the exact candidate routing rules, including `user` fields and order.
6. Publish matching Live artifacts.
7. Persist Desired inputs.
8. Promote the identity generation.

If any running-service step fails, the previous current generation, Desired
inputs, and Live artifacts remain in place or an explicit recoverable
`apply.error` is written. Desired must not advance before matching runtime and
Live state has been verified.

If the service is stopped, runtime-capable operations stage Desired inputs only
and publish no fake Live success. The candidate generation is exposed as the
current Desired identity read model, while its transaction remains pending until
the next service start compiles Desired into Live and recovery confirms that the
recorded candidate hashes match the actual Desired and Live artifacts.

## Limits

xp2p validates identity-dependent candidates before building Xray runtime state.

Current limits:

- 100 scoped groups in provider configuration;
- nested group depth 16;
- 10,000 resolved labels per redirect;
- 100,000 resolved labels per server candidate;
- 1 MiB serialized routing-rule data budget.

Exceeding a limit is a candidate validation error and leaves Desired, Live, and
the current identity generation unchanged.

## Secrets and diagnostics

Normal command output, service logs, audit events, and identity status must not
print provider secrets. Provider status should surface safety issues such as
insecure TLS without showing credentials.

Configuration export and diagnostic bundles intentionally preserve plaintext
Desired inputs, including provider secrets. Treat them as secret material.

## Advanced

LDAP over TLS, Keycloak HTTPS trust, insecure TLS, request timeouts, and page
sizes are provider-specific controls. Use them only when the directory requires
them:

```toml
[server.identity_provider.ldap]
url = "ldaps://ldap.example.internal:636"
timeout = "20s"
page_size = 500
insecure_tls = false
```

```toml
[server.identity_provider.scim]
timeout = "20s"
page_size = 200
insecure_tls = false
```

## Troubleshooting

If sync fails:

- verify that the provider is reachable from the server host;
- verify LDAP bind credentials or Keycloak bearer token access;
- verify that the Keycloak endpoint points at the Admin API realm path;
- check that subject and membership attributes point to immutable IDs;
- check that `group_ids` does not exclude all expected subjects;
- inspect `.state/identity/state.json` for the last sync status.

If a restricted redirect does not include an expected user:

- confirm the subject exists in `xp2p server identity status`;
- confirm the subject is in the expected provider group;
- confirm the subject is provisioned;
- run config rendering to validate the effective routing document.

If a redirect becomes `disabled_by_policy`:

- check whether all selected groups are empty, deleted, or out of scope;
- check whether matching identities are discovered but not provisioned;
- check whether the provider was detached or the cache became stale.

## Not supported

The current feature is allowlist-only. It does not support deny users or deny
groups, multiple simultaneous providers, self-service credential issuance, or
automatic credential generation during synchronization.
