# Поток применения

Этот документ описывает, как xp2p применяет изменения конфигурации двумя
согласованными путями:

- применение сервисом для ручных правок, деплоя, импорта, изменений уровня
  сервиса и изменений, которые нельзя обновить через закреплённый gRPC API Xray;
- применение командами CLI во время работы для ресурсов Xray, которые можно
  изменить и проверить через закреплённый gRPC API Xray.

Цель — сделать обновления конфигурации атомарными, аудируемыми и безопасными
для применения из сервисов без зависимости от флагов CLI.

## Ключевые файлы и директории

- `CONFIG_ROOT/.state/`
- `CONFIG_ROOT/.state/live/`
- `CONFIG_ROOT/.state/lkg/`
- `CONFIG_ROOT/.state/apply.request`
- `CONFIG_ROOT/.state/apply.error`
- `CONFIG_ROOT/xp2p-client.toml`
- `CONFIG_ROOT/xp2p-server.toml`
- `CONFIG_ROOT/config-client/`
- `CONFIG_ROOT/config-server/`

Файл `apply.request` — это триггер, который просит сервисный слой
скомпилировать и применить желаемые входные данные. Команды CLI, способные
применять изменения во время работы, не создают `apply.request`, когда успешно
применяют изменение через API Xray или только сохраняют желаемые входные данные
при остановленном сервисе.

## Роли

- Команды CLI, способные применять изменения во время работы: строят
  кандидатную конфигурацию до изменения желаемых входных данных, применяют и
  проверяют её через API Xray при запущенном сервисе, затем публикуют
  артефакты Live и сохраняют желаемые входные данные.
- Ручные правки, деплой, импорт, UI и изменения уровня сервиса: обновляют
  желаемые входные данные и создают `apply.request`.
- Сервисный слой (`xp2p run` или системный сервис): читает `apply.request`,
  компилирует желаемые входные данные в артефакты времени выполнения и
  выполняет очистку маркеров.

## Общий процесс

### Применение сервисом

1. Обновить желаемые входные данные (`xp2p-*.toml` и опциональные JSON-фрагменты).
2. Записать `apply.request`.
3. Сервис обнаруживает запрос и компилирует конфигурацию времени выполнения.
4. При успехе сервис удаляет `apply.request`, при ошибке пишет `apply.error`.
5. Состояние маршрутов ОС и TUN применяет только сервисный слой.

### Применение командой CLI во время работы

1. Загрузить текущие желаемые входные данные и построить кандидатную
   конфигурацию в памяти.
2. Проверить и скомпилировать кандидата без записи в Desired или Live.
3. Если запущенный Xray доступен, применить кандидата через gRPC API Xray.
4. Проверить состояние запущенного Xray.
5. При успехе опубликовать соответствующие артефакты Live и сохранить
   соответствующие желаемые входные данные.
6. Если сервис остановлен или запущенная Live-конфигурация недоступна, сохранить
   только желаемые входные данные. Следующий старт сервиса скомпилирует и
   запустит их.
7. Если сервис выглядит запущенным, но применение через API или проверка
   завершается ошибкой, вернуть ошибку и оставить Desired и Live без изменений.

## Желаемые входные данные

Желаемые входные данные всегда доступны для правки пользователем и лежат по стабильным путям:

- `CONFIG_ROOT/xp2p-client.toml`
- `CONFIG_ROOT/xp2p-server.toml`
- `CONFIG_ROOT/config-client/*.json` (опциональные JSON-фрагменты)
- `CONFIG_ROOT/config-server/*.json` (опциональные JSON-фрагменты)

xp2p читает эти входные данные и компилирует их в итоговую конфигурацию Xray,
которую использует процесс времени выполнения.

Рекомендованные имена JSON-фрагментов и точки вставки правил маршрутизации
описаны в [компиляции конфигурации](config-compilation.md).

## Правила чтения и исключения

- Поведение во время работы (`service run`, диагностика, ping, маршрутизация ОС)
  читает только Live-артефакты и никогда не читает желаемые входные данные напрямую.
- Ручные правки и изменения уровня сервиса запрашивают применение через
  `apply.request`.
- Команды CLI, способные применять изменения во время работы, могут сохранить
  желаемые входные данные при остановленном сервисе или обновить Live после
  проверенного применения через API при запущенном сервисе, не создавая
  `apply.request`.
- Проверка во время deploy может запустить временный xray-core с конфигом, скомпилированным
  из желаемых входных данных, но она не должна писать в Live и не должна обходить
  механизм применения.

## Правки и откат

Этот раздел описывает поток ручных правок, правок через CLI во время работы,
сервисного применения и отката с разделением Desired, Live и LKG. Запросы
сервисного применения отслеживаются маркерным файлом.

### Роли директорий

- Desired: редактируемые пользователем входные файлы конфигурации
  - `CONFIG_ROOT/xp2p-*.toml`
  - `config-client/*.json`, `config-server/*.json`
- Live: активная конфигурация времени выполнения
  - `CONFIG_ROOT/.state/live/`
- LKG: последний рабочий снимок (скрытый)
  - `CONFIG_ROOT/.state/lkg/`

Live и LKG хранят скомпилированные артефакты времени выполнения (например
`xray.json`) вместе с метаданными применения.

### Ручные правки

1. Пользователь редактирует Desired файлы в `CONFIG_ROOT/` или `config-*/`.
2. Наблюдатели сглаживают серии изменений.
3. После стабилизации правок создаётся `apply.request`, чтобы запустить применение в сервисе.
4. Сервис компилирует желаемые входные данные и атомарно пишет Live-артефакты.
5. При успехе предыдущий набор Live-артефактов сохраняется как LKG (опционально).

### Правки через CLI во время работы

1. CLI строит и проверяет кандидатную конфигурацию из текущих желаемых входных
   данных.
2. Если сервис запущен, CLI применяет кандидата через API Xray и проверяет
   результат во время работы.
3. При успехе CLI пишет Live-артефакты, соответствующие состоянию запущенного
   Xray, и сохраняет соответствующие желаемые входные данные.
4. Если сервис остановлен, CLI сохраняет только желаемые входные данные и не
   меняет Live.
5. Если применение или проверка во время работы завершается ошибкой, CLI
   возвращает ошибку и оставляет Desired и Live без изменений.

### Правки через CLI и UI с применением сервисом

1. CLI или UI записывает в желаемые входные данные изменения, которые нельзя
   применить во время работы.
2. Создаётся `apply.request`, чтобы запустить применение в сервисе.
3. Сервис компилирует желаемые входные данные в Live-артефакты.
4. При успехе предыдущий набор Live-артефактов сохраняется как LKG (опционально).

### Откат

1. Применение завершается ошибкой (ошибка сервиса, Xray или проверки здоровья).
2. Сервис восстанавливает Live-артефакты из LKG (если доступно).
3. Записывается `apply.error` с идентификатором запроса и причиной.
4. `apply.request` остаётся, чтобы оператор видел запрошенное изменение, но сервис
   пропускает повторные попытки применения для того же идентификатора запроса.
5. Сервис перезапускается, используя восстановленные Live-артефакты, и логирует ошибку.

## Запрос на применение

Файлы-триггеры применения создаются по путям:

- `CONFIG_ROOT/.state/apply.request`
- `CONFIG_ROOT/.state/apply.error`

Внутри хранится роль (`client` или `server`) и идентификатор запроса. Сервисный
процесс наблюдает за этим файлом и рассматривает его как единственный источник
истины для работы по применению. При ошибке применения сервис пишет
`apply.error` с тем же идентификатором запроса и причиной.

## Применение сервисом

При старте (или рестарте) сервис:

1. Читает `apply.request`.
2. Компилирует желаемые входные данные в Live-артефакты.
3. Удаляет `apply.request`.
4. Пишет метаданные LKG при успехе (опционально).

Если применение завершается ошибкой, сервис логирует ошибку и оставляет
`apply.request`, чтобы оператор мог расследовать проблему или повторить попытку.
Сервис не будет повторять применение для того же идентификатора запроса после
записи `apply.error`; после исправления желаемых входных данных нужно создать
новый запрос применения.

## Маршруты и изменения ОС

Изменения ОС применяются только сервисным слоем:

- Создание TUN и назначение IP.
- Маршруты и изменения full-tunnel.
- Переопределения DNS (если включено).

Команды CLI и UI не меняют состояние ОС напрямую. Изменения, влияющие на ОС,
обновляют желаемые входные данные и запрашивают применение сервисом. Команды CLI,
способные применять изменения во время работы, могут менять ресурсы Xray через
API, но TUN, маршруты, DNS, файрвол и nftables остаются во владении сервиса.

## Контракт состояния ОС в рантайме (TUN / маршруты / DNS)

Этот раздел определяет контракт service-owned OS state, чтобы избежать видимого "flapping" при рестартах.

### Владение и область

- Service layer владеет OS state (TUN, routes, DNS).
- Service layer обязан поддерживать OS state в соответствии с текущим Desired runtime mode.
- CLI/UI/ручные правки не должны напрямую менять OS state.

### Переходы, управляемые режимом

Переходы OS state определяются сменой mode, а не внутренними рестартами:

- Вход в full-tunnel (`client.tun_enabled=true` и `client.tun_mode=full`):
  - Заменить default routes на TUN интерфейс.
  - Добавить bypass routes для всех настроенных endpoints.
  - Применить DNS override на `client.dns_servers` (если настроено).
  - Держать full-tunnel активным, пока Desired остаётся в full-tunnel mode.
- Выход из full-tunnel (Desired уходит из full-tunnel):
  - Восстановить базовые default routes и убрать bypass routes.
  - Восстановить базовый DNS.
- Stop/uninstall сервиса:
  - Восстановить базовые routes/DNS (best effort) перед завершением.

### Семантика рестартов и отмены

Рестарты сервиса из-за `apply.request`, file watchers, health checks или crash recovery не должны вызывать
rollback routes/DNS, если Desired остаётся в full-tunnel mode.

- Отмена child-run (graceful restart) не является сменой mode.
- Rollback/restore разрешён только при явном stop, явной смене mode или при hard failures, требующих выхода из mode.

### Состояние ожидания и повторы (Windows)

На Windows готовность TUN может быть задержана или нестабильна между рестартами (адаптер отключён, IPv4 отсутствует, DAD не preferred).
Когда Desired — full-tunnel, но адаптер не готов, runtime входит в pending state вместо rollback OS state.

- Pending state записывается в `CONFIG_ROOT/xp2p-client.tun-full.json` как `phase = "full_pending"` со стабильным `pending_reason`.
- Пока pending, routes и DNS override не применяются.
- Сервис повторяет попытки через рестарты с exponential backoff (2s, 4s, 8s, ... максимум 30s), пока адаптер не станет `up`/`preferred`.

## Переключение режимов

Смена режимов (split/full):

- Обновить `tun_enabled`, `tun_mode` и `full_tunnel_tag` в Desired TOML.
- Записать `apply.request`.
- Сервис компилирует конфиг и перезапускает runtime при необходимости.
- В full режиме повторное применение routes не переписывает конфиг; оно лишь
  обновляет OS routes.

## Частые причины ошибок

- Невалидный Desired TOML / невалидные JSON snippets.
- Коллизии при merge (зарезервированные теги, неверный порядок правил, конфликты).
- Сервис не запущен или apply request не обнаружен.
- Ошибка применения через API или проверки для команды CLI, способной применять
  изменения во время работы.
