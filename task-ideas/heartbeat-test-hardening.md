# Усиление тестов heartbeat и state-cache

## Проблема

После восстановления туннеля реальный ping работал, но `xp2p client state` продолжал показывать `dead` с временем примерно на час старше текущего UTC. С увеличенным TTL запись считалась живой. Это указывает на отдельный дефект обновления heartbeat или state-cache.

Текущие интеграционные проверки местами слишком слабые: после ошибки ожидания свежей `alive`-записи тест принимает сам факт наличия тега. Такой fallback скрывает устаревший timestamp и ошибочный статус. Старый unit-тест также принимал искусственное время `now - 1h`, потому что проверял только итоговый `dead` при коротком TTL.

## Что требуется проверить

- Успешный heartbeat сохраняет актуальный timestamp, `healthy=true` и ожидаемый статус.
- Ошибка heartbeat не маскируется синтетическим временем и содержит диагностируемое состояние.
- Переходы `alive → dead → alive` корректно отражаются после восстановления control path.
- Перезапуск сервиса не оставляет устаревшую запись в кэше.
- `xp2p client state` использует согласованные часы и TTL без скрытого часового смещения.
- Failure dump содержит полное дерево `.state`, heartbeat-файл и релевантные логи.

## Предлагаемые изменения тестов

- Усилить `go/internal/client/heartbeat_runner_test.go`: проверять диапазон timestamp, `healthy` и причину ошибки.
- Расширить heartbeat helper параметрами ожидаемого статуса, допустимого возраста и признака здоровья.
- Удалить fallback «достаточно наличия тега» из Linux/OpenWrt tunnel fixtures.
- Добавить интеграционный сценарий восстановления control path и обязательное ожидание свежей `alive`-записи.
- Добавить отдельную проверку state-cache после обновления пакета и рестарта сервиса.

## Критерии готовности

- Искусственное смещение timestamp на час гарантированно ломает тест.
- Наличие старой записи без свежего heartbeat не считается успехом.
- После восстановления тест требует `alive` в пределах заданного временного окна.
- Проверки не ослабляются увеличением TTL как основным способом устранения ошибки.
