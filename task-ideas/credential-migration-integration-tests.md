# Интеграционные тесты миграции credentials

## Проблема

При ротации credential сервер хранит новый credential как активный, а старый — как `previous`. Клиент со старым Live runtime должен авторизоваться через `previous`, получить активный credential, применить его к работающему туннелю, сохранить одинаковое состояние в Desired и Live и подтвердить миграцию серверу.

Инцидент на рабочем устройстве показал, что отдельные части этого сценария покрыты тестами, но полного upgrade-сценария с реальным старым клиентским состоянием нет. Кроме того, в Linux-интеграционных тестах осталась проверка автоматической ротации при старте сервиса, хотя такое неявное изменение пользовательских credentials больше не является желаемым поведением.

## Что требуется проверить

- Сервер после явной ротации принимает control-auth как по активному, так и по `previous` credential в течение окна миграции.
- Клиент со старым credential получает новый credential через control plane.
- Новый credential сначала применяется и проверяется в работающем Xray, затем атомарно публикуется в Desired и Live.
- После успешного подтверждения сервер очищает `previous` в соответствии с правилами ротации.
- Ошибка runtime apply не изменяет Desired и Live и не подтверждает миграцию.
- Повторный запуск миграции идемпотентен.
- Перезапуск клиента и сервера после миграции не возвращает старый credential.

## Предлагаемое размещение

- Unit-тесты ротации оставить в `go/internal/server/users_rotation_test.go`.
- Полный Linux-сценарий вынести из перегруженного `tests/host/linux/test_subscription_control_plane.py` в отдельный модуль `tests/host/linux/test_credential_migration.py`.
- Для OpenWrt добавить upgrade-сценарий рядом с `tests/host/openwrt/test_package_upgrade.py`, используя предыдущий релизный IPK и текущий кандидат.
- Общие операции чтения и сравнения credentials оформить в небольшом специализированном helper-модуле, не расширяя `env.py`.

## Тестовые данные

Использовать только синтетические значения: вымышленные имена endpoint, UUID и секреты. Реальные `/etc/xp2p` архивы допускаются только как локальный источник структуры после обезличивания и не должны попадать в Git, test output или failure dumps.

## Критерии готовности

- Тест падает, если клиент остаётся на `previous` credential.
- Тест падает, если Desired, Live и фактический Xray расходятся.
- Тест падает, если подтверждение отправлено до успешной runtime-проверки.
- Устаревший тест принудительной ротации при старте заменён проверкой сохранения credentials.
- Сценарии проходят в штатном релизном прогоне Linux/OpenWrt.
